What the research says

Twelve parallel research streams across process notation standards, the SOP tooling market, canvas libraries, ISO/EOS versioning conventions, and the systemisation literature. The signal was unusually consistent.

01 / NOTATION

BPMN is a trap. Swimlanes win.

Teams use ~8 of BPMN's 100+ constructs. The learning curve kills adoption. Swimlanes with named lanes + explicit handoffs give 80% of the value at 20% of the effort — and non-technical staff read them instantly.

02 / DEPTH

Two levels. Then stop.

L1 end-to-end process, L2 sub-process swimlane. Don't decompose to task level. Every framework that tried L5 granularity produced shelfware.

03 / COUNT

EOS says 6–10 core processes. Max 12.

Not departments, not workflows — the vital few that actually differentiate you. Your instinct that "sales and marketing were never defined" is exactly the gap EOS predicts in owner-led agencies.

04 / OWNERSHIP

Named owner or it doesn't exist.

Promapp separates Process Owner (approves changes) from Process Expert (runs it daily). Changing the owner is itself a revision event. Vague ownership is indistinguishable from no ownership.

05 / CADENCE

Documentation dies without a heartbeat.

Every source agrees: weekly tactical, quarterly review, annual refresh. A process with no scheduled review date becomes a liability within two quarters.

06 / THE GAP

No product does all three.

Trainual links goals→KPIs. Promapp does governance. Gluu does continuous improvement. None combine versioned owned processes + explicit goals + hours that feed estimation. Conductor already has the hours.

07 / VERSIONING

ISO 9001 §7.5 already wrote your schema.

Version number, effective date, reason-for-revision, approver, and a draft→review→published state machine. Plus acknowledgement records so you know who has actually read rev 4.

08 / CANVAS

React Flow, if you need free drag.

@xyflow/react v12 — MIT, ~155KB, arbitrary React nodes, nested sub-flows via parentId. Pair with Dagre for auto-layout. tldraw is the fallback but is now $6k/yr commercial.

09 / IN CONDUCTOR

You are 60% built already.

process_steps already carries department + estimated_hours and is the allocation source of truth via service_allocation_resolved. What's missing: processes untethered from a service, goals, nesting, and versions.

Five concepts

These are not five skins on the same idea. Each makes a different bet about what the primary object is — a hierarchy, a canvas, a spec, a document, or a revision. Click through and see which one feels like how you actually think.

How it works

  • Fixed top-level frame. The four bands (Attract / Convert / Deliver / Retain) are structural, not drawn. You slot processes into bands, and the layout does itself.
  • Unmapped is a first-class state. The Atlas shows gaps as red blocks. Your sales and marketing systems appear as visible holes in the map the day you turn it on — which is exactly the diagnosis you're after.
  • Zoom, don't pan. Click a process → its L2 swimlane opens full-screen with departments as lanes. Click a step → L3 detail panel. There is no infinite canvas to get lost in.
  • Goals cascade. Each band has a goal, each process has a goal, each step has a "definition of done". A child goal that doesn't ladder into its parent is flagged.
  • Hours roll up. Step hours sum into process hours, sum into band hours. You get a real answer to "how many hours per week does selling cost us?" — which today lives only in the sales-bd overhead category.

Where it's weakest

  • No free drag. If you want to sketch a messy idea in a workshop, this fights you.
  • Branching and decision logic are awkward — it's a ladder, not a graph.
  • The rigidity that makes it tidy also makes it feel like a form, not a drawing board.

Data model

-- hierarchy is the spine create table process_definitions ( id uuid primary key, parent_id uuid references process_definitions, band text, -- attract|convert|deliver|retain level int, -- 0 | 1 | 2 name text, goal_statement text, -- required at every level goal_metric text, owner_id uuid references team_members, service_id uuid references services, -- nullable! review_due_at date, ordinal int ); -- steps reuse the existing shape alter table process_steps add column definition_id uuid, add column goal_statement text, alter column service_id drop not null;

Effort

  • No new npm dependency — CSS grid + the existing WorkflowTimeline patterns.
  • Two new tables, one column set on process_steps.
  • ~2–3 weeks to a usable Atlas + L2 swimlanes.

How it works

  • React Flow (@xyflow/react v12). MIT licensed, ~155KB, nodes are arbitrary React components — so a block can render an avatar stack, an hours pill and a goal chip natively, styled with your M3 tokens.
  • Swimlanes are group nodes. Drag a block into a lane and it inherits that lane's department. Lane header shows the rolled-up hours live.
  • True nesting. React Flow's parentId gives you real sub-flows — double-click "Proposal" and you're inside its own canvas. Depth is unlimited (you should still cap it at 2).
  • Dagre for tidy-up. One button re-flows the graph automatically when a workshop leaves it messy.
  • Persistence. The whole graph serialises to a single jsonb blob — which makes snapshot versioning trivially easy and matches the sow_documents.body pattern you already use.

Where it's weakest

  • Infinite canvas = infinite mess. Every agency that bought Miro has a graveyard of half-finished boards. Freedom is the feature and the failure mode.
  • Hours live in a JSON blob, so wiring them into service_allocation_resolved means either a sync job or a shadow normalised table.
  • Two people editing the same graph needs conflict handling you don't have today.
  • Biggest build. Realistically the last thing you ship, not the first.

Data model

create table process_graphs ( id uuid primary key, name text, kind text, -- service | system | subprocess service_id uuid references services, -- nullable owner_id uuid references team_members, goal_statement text, current_revision_id uuid ); create table process_graph_revisions ( id uuid primary key, graph_id uuid references process_graphs, revision int, body jsonb, -- {nodes:[], edges:[]} schema_version int, state text, -- draft|review|published reason_for_change text, approved_by uuid, approved_at timestamptz, effective_date date, unique (graph_id, revision) ); -- mirrored into a flat table by trigger so hours -- can still feed service_allocation_resolved

Effort

  • One new dependency pair (~180KB gzipped total).
  • Custom node components, lane logic, inspector, autolayout, serialisation, conflict handling.
  • ~5–7 weeks to something you'd trust the team with.
CONCEPT 03 — DATA FIRST, DIAGRAM AS OUTPUT

The Spec

The contrarian one. You don't draw the process — you specify it, and the diagram draws itself. Editing happens in a fast structured table where you tab through steps, owners, goals and hours. The swimlane view is a generated, always-tidy render of that data. Crucially: the hours you type here are the estimate. Documenting a process and scoping it become the same act.

How it works

  • Extends what already exists. process_steps already has department + estimated_hours and already drives service_allocation_resolved. You add: a nullable service_id (so a process can be pure system, not a service), a goal per process and per step, and a definition-of-done field.
  • The diagram is a view, not a document. Toggle to swimlane and it renders from the same rows — always tidy, no layout to maintain, no drift between "the picture" and "the truth".
  • Documentation and estimation collapse into one act. This is the killer property. Today you scope, then separately (never) document. Here, the only way to change the estimate is to change the process — so your scoping gets more accurate as a side effect of the systemisation work you already want to do.
  • The reality check panel. Because Conductor already has project_actuals, every process can show est-vs-actual across its last N runs. That's the feedback loop every systems book insists on, and no SOP product on the market has it.

Where it's weakest

  • It isn't a drawing board. It won't feel creative in a workshop.
  • Branches, loops and decisions are clumsy in a linear list.
  • Non-linear systems (marketing especially) don't fit a numbered ladder cleanly.

Data model

The 99.5-100.5 trigger still guards.

Effort

  • Two migrations. No new dependency. Rework of ProcessFlow.tsx into a proper editor.
  • Swimlane renderer reuses WorkflowTimeline patterns you already have.
  • ~1.5–2 weeks. By far the cheapest path to real value.

How it works

  • A fixed template, not a blank page. Purpose/goal, trigger, steps, definition of done, exceptions. The template is the discipline — you cannot publish without a goal.
  • The diagram is free. Steps are structured rows, so the vertical flow renders itself. No layout work, no divergence between the picture and the words.
  • Acknowledgement is the point. Straight out of ISO 9001 §7.5 and Promapp. When rev 5 publishes, everyone affected gets it in their queue and must mark it read. You get a live "who's on the old version" board — which is a direct answer to "work isn't hitting the standard".
  • Exceptions are first-class. Every systems book says the same thing: what kills a process isn't the happy path, it's the undocumented edge case. Giving exceptions their own field is a small change with outsized effect.
  • Best fit for sales & marketing. These aren't neat DAGs — they're rhythms, judgement calls and triggers. Prose handles that where a flowchart fights it.

Where it's weakest

  • Least visual of the five. It's a wiki with a diagram attached, and wikis go stale.
  • You explicitly asked for a drawing board. This isn't one.
  • Acknowledgement can become a rubber-stamp ritual if the cadence isn't real.

Data model

  • Auto-diagram reuses existing block components.
  • ~2–3 weeks including the acknowledgement queue.
CONCEPT 05 — GOVERNANCE FIRST

The Ledger

Git, for how the business works. Anyone on the team can open a proposal against any process — a private draft branch. They move blocks, retime steps, add a reason for the change, and submit. The owner sees a visual diff: added blocks glow green, removed ones strike through red, retimed ones amber. Approve and it becomes rev 5 with a permanent changelog entry. You can scrub back through time and watch how the business evolved.

How it works

  • Every revision is immutable. Nothing is ever edited in place. This matches the append-only project_actuals → project_actuals_current idiom already used throughout Conductor.
  • Proposals unlock the team. You said whole-team-contributes with approval gating. This is that, exactly. A junior can fix a process they run daily without anyone fearing they'll break it — the owner sees a diff, not a mystery.
  • Reason-for-change is mandatory. Straight from ISO 9001. Over a year you accumulate a narrative of why the business works the way it does, which is the single most valuable artefact here and the thing every other tool loses.
  • Time-scrubbing. Drag a slider and see what the process looked like in March. Pair it with actuals and you can ask: did rev 4 actually make things better?
  • It is a layer, not a rival. Honest framing: the Ledger sits on top of whichever editor you pick from concepts 1–3. It's the governance skin.

Where it's weakest

  • Ceremony can throttle contribution. If approving a proposal takes a week, people stop proposing.
  • Needs an underlying editor to be useful — it can't ship first.
  • Visual diffing of a free-form graph (concept 2) is genuinely hard. Diffing an ordered step list (concepts 1/3) is easy. That's an argument for pairing it with 1 or 3.

Data model

create table process_revisions ( id uuid primary key, definition_id uuid references process_definitions, revision int not null, body jsonb, -- full snapshot state text, -- draft|proposed|published|superseded reason_for_change text not null, proposed_by uuid, proposed_at timestamptz, approved_by uuid, approved_at timestamptz, effective_date date, supersedes_id uuid, diff_summary jsonb, -- {added:[],removed:[],changed:[]} unique (definition_id, revision) ); -- one live published revision per process create unique index proc_one_live_idx on process_revisions (definition_id) where state = 'published'; -- mirrors quotes_one_live_per_scope_idx exactly

Effort

  • One table, one state machine, a diff renderer. jsondiffpatch for structural comparison.
  • Reuses your existing approval patterns from extension_requests / revision_requests.
  • ~2–3 weeks on top of an existing editor.

What I'd actually do

Concepts 1, 2 and 3 are genuinely rival bets on what the primary object is. Concepts 4 and 5 are layers that can sit on any of them. So the real question isn't "which one" — it's "which spine, and in what order do the layers land".

My read: The Spec (03) is the spine, The Atlas (01) is the navigation, The Ledger (05) is the governance, and The Drawing Board (02) is the greenfield tool you add last — because the thing that makes Conductor special is that hours already mean something here. No SOP product on the market can tell you that your documented process says 14.5h and reality says 17.2h. That loop is your unfair advantage, and it only exists if the process data is structured, not a canvas blob.

PHASE 1
~2 wks
Spec spine — untether process from service
Make process_steps.service_id nullable, add process_definitions with a mandatory goal, add goal + definition-of-done per step. Rebuild ProcessFlow.tsx into a real editor with the live allocation and reality-check panels. You can document the sales system on day one — and its hours land in the same place your service hours do.
PHASE 2
~2 wks
Ledger — revisions, proposals, diffs
Immutable process_revisions with mandatory reason-for-change, a proposal state machine reusing your extension_requests approval pattern, and a step-list diff view. Diffing an ordered list is easy; this is why the Spec comes first. Now the whole team can contribute without you fearing the map.
PHASE 3
~2 wks
Atlas — the L0 business map
The four bands, nine processes, and the red "unmapped" blocks. This is the artefact you'll actually put on a screen in a leadership meeting. Cheap once the data exists — it's a query and a grid. Adds the drill-down and the roll-up hours per band.
PHASE 4
~1.5 wks
Playbook layer — prose fields + acknowledgement
Add trigger, exceptions and the acknowledgement queue to the existing process record. This is the piece that attacks "work isn't hitting the standard" directly — a live board of who is still working off rev 3.
PHASE 5
~4 wks · optional
Drawing Board — React Flow canvas for greenfield design
Add the free canvas as a drafting mode for processes that don't exist yet. Sketch the marketing system on the canvas in a workshop, then "commit to spec" — which converts the graph into structured steps. You get the workshop feel without the shelfware risk, because the canvas is a doorway, not the destination.
The honest risk: every source in the research agreed that documentation dies without a cadence. Whichever concept you pick, the thing that determines whether this works isn't the software — it's whether a named owner reviews their process every quarter and whether proposals get approved within days, not weeks. EOS says 6–10 core processes, maximum 12. If Conductor ends up holding 40 process maps, it has already failed. Build the review cadence into the tool before you build the fifth feature.
