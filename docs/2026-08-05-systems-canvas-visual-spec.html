These colours aren't invented — departments.color already exists in your schema and is already used across Conductor. The canvas just reads it.

What lanes were doing, and where it went

Three jobs. Two of them didn't need a container in the first place.

Kept — moved somewhere better

Same signal, less furniture

  • Who owns this step → the coloured spine plus a named avatar on the block. At 6–12 blocks per process this reads faster than scanning which row a block sits in.
  • Hours per department → the roll-up strip along the bottom. It was always a computed number; drawing a box around blocks to get it was doing the sum by eye.
  • Handoffs → the connector. When the department changes between two blocks, the arrow goes amber and says ⇄ Handoff. This is more visible than a lane jump, and it maps directly onto the process_step_handoffs view you already have — so it can later show real wait time between steps.

Genuinely lost

Worth knowing before you commit

  • Scanning one person's whole day. With lanes you can trace a row and see everything Lisa touches. Without them you're picking purple blocks out of a graph. Fix: a "highlight by person" filter — one click dims everything else. Cheap to add.
  • Legibility past ~20 blocks. Colour coding degrades as block count rises. But the research was blunt on this: if a process needs 20+ blocks it's two processes. The constraint is a feature.
  • Empty-lane gaps. The "Nurture — nobody owns this" prompt was doing real work in the lane version. Replaced with a red dashed ghost block, which is arguably louder anyway.

What this saves you

Dropping lanes isn't just visual simplification — it removes the single fiddliest part of the React Flow build.

Build complexity

  • No parentId group nodes for lanes — which means no child-position-relative-to-parent maths, no lane resize handling, no "block dragged half out of its lane" edge cases.
  • Nesting still uses parentId, but only for genuine sub-processes, which is the well-trodden path in React Flow.
  • Auto-layout via Dagre gets simpler — laying out a flat graph is a solved problem; laying out a lane-constrained graph means constraining ranks per lane.
  • Realistically ~1 week off the estimate. Call it 4–6 weeks rather than 5–7.

Data model — simpler too

-- no lane entity at all create table process_blocks ( id uuid primary key, graph_id uuid references process_graphs, parent_id uuid references process_blocks, title text, goal_statement text, department_id uuid references departments, owner_id uuid references team_members, estimated_hours numeric(6,2), pos_x int, pos_y int ); -- handoff = department change across an edge. -- derived, never stored: create view process_block_handoffs as select e.*, true as is_handoff from process_edges e join process_blocks a on a.id = e.source join process_blocks b on b.id = e.target where a.department_id is distinct from b.department_id;
One thing to decide later, not now: a person who spans two departments. Jamie is SEO but runs some account work — is her block teal or purple? The clean answer is that the block has a department (it's work, and work belongs to a department for costing) while the person is just who does it. That keeps colour meaningful for the hours roll-up and keeps allocation consistent with how service_allocation_resolved already works — per department, never per person. Worth confirming when you build the inspector.
