## Execution ground rules

These override the spec's suggestions where they conflict. Each was verified against the
live repo/DB, not assumed.

1. **One worktree, phases in sequence.** The spec says P1 and P2 may run in parallel
   worktrees. They must not. P1/P2/P3 all edit `supabase/functions/push-to-clickup/index.ts`,
   and P2–P6 all issue DDL against the *single* live project `lpgwxacoqiqpcfpkklib` — there is
   no branch database. Parallel worktrees would mean merge conflicts on one file plus
   concurrent DDL on one DB.

2. **Migration numbers are assigned here, not by agents.**

   | Number | File | Phase |
   |---|---|---|
   | 0104 | `0104_process_steps_nesting.sql` | P2 |
   | 0105 | `0105_system_kinds_materialise.sql` | P3 |
   | 0106 | `0106_system_definitions.sql` | P4 |
   | 0107 | `0107_system_revisions.sql` | P5 |
   | 0108 | `0108_system_edges_positions.sql` | P6 |

3. **Every migration is written to `supabase/migrations/` AND applied via
   `mcp__cc-supabase__apply_migration`.** Never `supabase db push`. The DB records migrations
   with a *timestamp* version and a bare snake_case name (last row:
   `20260804082034 / services_checklist_items`), so the file's `010N_` prefix is a repo
   convention only — pass the bare name to the MCP tool.

4. **Edge functions deploy with `verify_jwt: false`.** The gateway cannot validate this
   project's ES256 user tokens; a default-`true` deploy breaks the function in production.

5. **Test bar is delta-against-baseline, not zero.** Captured on the baseline commit:

   | Check | Baseline | Command |
   |---|---|---|
   | `tsc -b` | **65** pre-existing errors | `npx tsc -b --force` (`tsc -p` is a false pass) |
   | vitest | **7** failures in 3 files (`RetainersList`, `RetainerBurnSection`, `StatusStrip`) | `npm test` |
   | deno | **131 passed / 0 failed** | `deno test --allow-all supabase/functions/_shared/` |
   | `service_allocation_resolved` | hash `6668abfe9d76c8d2d8d8e5935d3d2753`, 212 rows, 983.38h | snapshot query below |

   Deno must stay at 0 failures. tsc and vitest must not exceed baseline.

   ```sql
   select md5(string_agg(service_id::text||'|'||department_id::text||'|'||coalesce(pct::text,'-')
              ||'|'||coalesce(price_share_cents::text,'-')||'|'||coalesce(hours::text,'-'),
              E'\n' order by service_id, department_id)) as snapshot_hash,
          count(*) as row_count, round(sum(hours),2) as total_hours
   from service_allocation_resolved;
   ```

6. **Dev server on port 5174** in this worktree (free; prod runs from the main checkout on
   5391). Never `pkill -f vite` — it kills prod. `.env.local` is already copied in.

## Corrections to the spec (verified defects, must be applied)

The spec was written before these were checked. Each is confirmed against the current code.

### C1 — `buildBriefTaskBody` cannot honour `estimated_hours` (blocks P1)

`_shared/clickup.ts:189` derives the estimate from points, not hours:

```ts
time_estimate: Math.round(input.sprintPoints * POINT_TO_MIN * 60_000)   // POINT_TO_MIN = 15
```

Phase 1 tells us to pass `sprintPoints = min(10, max(1, round(hours/4)))`. A 4.0h step →
1 point → **15 minutes**, contradicting Phase 1's own acceptance criterion ("a time estimate
matching `estimated_hours`"). **Fix:** add an optional `timeEstimateMs?: number | null` to
`BriefTaskInput`; when present it overrides the points-derived value. Existing callers
(`schedule-brief-tasks`) omit it and are unaffected.

### C2 — `push-to-clickup` template-step query has no `parent_id` filter (blocks P2)

`push-to-clickup/index.ts:~573` selects every `process_steps` row for the quote's services and
maps *all* of them into `process_step_instances` + one `[Step N]` ClickUp task each. The moment
0103 adds `parent_id`, sub-steps get their own instances and their own tasks — double-counted,
and duplicated again as checklist items. **Fix:** add `.is("parent_id", null)` in P2, in the
same change that adds the column.

### C3 — React Query keys break when `service_id` goes nullable (blocks P4)

`useProcessSteps.ts` keys and invalidates on `d.service_id` (L11, L38, L50, L62). Once P4 makes
`service_id` nullable, a system-scoped step invalidates `["process_steps", null]` and the UI
silently stops refreshing. **Fix:** key on `system_id ?? service_id`.

### C4 — flat-rewrite hooks destroy nesting (blocks P2/P4)

`useReplaceSteps` and `useSetServiceChecklist` both `delete().eq("service_id", …)` then reinsert
a flat list. After 0103 that silently deletes every sub-step. **Fix:** scope both deletes to
`.is("parent_id", null)` and cascade handles children, or preserve/re-parent explicitly.

### C5 — allocation snapshot must be re-checked after P4, not only P2

The spec mandates the before/after `service_allocation_resolved` guard for P2 only. But
`alter column service_id drop not null` (P4) is the other moment the view can shed rows — both
its `step_sums` CTE and the `tree` existence check pivot on `service_id`. Re-run the snapshot
compare after P4.

### C6 — skip `jsondiffpatch` (P5)

Not in the locked Decisions list, and the required diff is an ordered-list compare over five
named fields — ~30 lines of pure TS, unit-testable, no dependency, no bundle cost.

### Migration 0109 — added during P7, not in the original plan

Two defects the per-phase verifiers missed because neither is visible from inside a single phase:

- **`process_steps_ordinal_idx` was never widened for `system_id`.** 0103 created it over
  `(service_id, parent_id, ordinal)`; 0105 added `system_id` and made `service_id` nullable but
  left the index alone. Two different systems each holding a top-level step at ordinal 1 both
  coalesce to `(sentinel, sentinel, 1)` and collide. The e2e suite was the first thing to create
  rows in that shape.
- **`system_id` was only ever stamped by the 0105 backfill.** Every service-editor write path
  (`useCreateStep`, `useReplaceSteps`, `useSetServiceChecklist`) inserts `service_id` with no
  `system_id`, so a `kind='service'` system read as stepless the moment anyone edited its
  service. Now stamped by a trigger at the source rather than worked around per-reader.

### Left for the user

1. **A live ClickUp push.** The spec's manual acceptance ("push a quote for a service with
   nested steps and confirm the subtask/checklist shape by eye") writes real tasks into a client
   workspace. Request bodies and plan objects are asserted in unit tests; the artefacts are not.
   This is the only evidence for P1/P2/P3's *live* acceptance. Note the 0103 data migration ran
   over **zero** rows, so the `checklist_items` absorption path has never seen real data.
2. **There is no add-step UI.** Steps can be edited but not created from any surface. P4's
   "given steps with hours" and P6's "drag a block onto the canvas" therefore cannot be
   performed — the e2e suite inserts steps DB-direct for exactly this reason. Everything
   downstream works only for the 2 systems that inherited steps from the 0105 backfill.
3. **Staff cannot propose a revision.** The spec's Phase 5 acceptance says they can; the spec's
   own Out-of-scope list says a staff-facing systems view is out of scope, and `/systems` sits
   behind `RequireAdmin`. Contradiction in the spec — needs a product decision, not a policy tweak.
4. **A published revision plus a service-editor rewrite silently yields zero step tasks.**
   `push-to-clickup` drops body steps whose ids no longer exist (correctly, to avoid a 23503),
   and the service editor deletes-then-reinserts with fresh ids. Dark today — zero revisions
   exist — but it lands the first time someone publishes and then edits the service.
5. **Three things are wired but dark:** the `system_handoffs` view (no readers — the canvas
   computes handoffs client-side), the published-revision materialisation branch (no system has
   a `current_revision_id`), and the `kind='internal'` ClickUp guard (structurally unreachable
   while steps are reached via `service_id`).
6. **The step-assignee fallback chain has no test.** It lives inline in `push-to-clickup`;
   the plan asked for coverage and it was not delivered.
