1. What a System is

A named, owned, goal-bearing way of doing something. The process behind the price.

TermMeaning
SystemThe top-level object. Has a goal, an owner, and steps.
StepOne unit of work inside it. Normally becomes a ClickUp task.
Sub-stepDetail within a step. Becomes a checklist item on that step's task.
CanvasThe drag-and-drop view of a system. A view, not the product.
RevisionAn immutable published version. Only published revisions reach ClickUp.

Four kinds

KindLinks toUse it for
serviceA serviceHow a sellable service actually gets delivered.
recurringA retainer recurring serviceRepeating retainer work.
internalA time categorySales, marketing, admin. Never creates ClickUp tasks.
referenceNothingA documented process that isn't billed or tracked.

2. Creating a system

Go to Systems in the nav, then + New system.

1
Name — e.g. "Outbound sales".
2
Kind — picking this changes the next field.
3
The link — Service, Recurring service or Time category, depending on kind. reference needs none. This is enforced by a database constraint, so a mismatch fails the save rather than creating something half-formed.
4
Band — attract, convert, deliver, retain, internal. Purely for grouping the list.
5
Goal statement — mandatory. "What does this system exist to achieve?" There is no way to create a system without one; that is deliberate.

Finding systems later

The left rail filters by Band, Kind, and a Health checkbox: Unmapped / no goal.

Start with the Unmapped filter

Every existing service with process steps was auto-converted into a system, with the placeholder goal "TODO: set a goal for this system". Those are the ones the Unmapped filter surfaces. Writing real goals for them is the first useful pass through this feature.

3. Adding steps

Two routes in, both landing in the same place.

  1. Open the system, find the Steps card, and click + Add step.
  2. A step called "New step" appears, unassigned and with no hours.
  3. Click its block on the canvas below and fill in the inspector: title, goal, department, responsible, estimated hours, and Materialise as.
  4. Drag it into place and connect it to the steps either side.

This works for every kind of system, including internal and reference ones that have no service behind them.

The other route, for service systems

Services → [the service] → Process flow → Add step also works, and is the better place when you are thinking about the service's costing rather than its process. Steps added either way show up in both places — a database trigger stamps each one with its service's system as it is written, so nothing needs linking by hand.

Sub-steps

Sub-steps carry no hours — only top-level steps do. That's enforced by a constraint, and it's what keeps the service allocation percentages correct.

4. The canvas

On the system detail page. Lane-free by design: department is a colour, person is an avatar.

Reading a block

  • Coloured left spine — the department, straight from departments.color.
  • Avatar + name — who is responsible.
  • Monospace pill — estimated hours.
  • Red dashed block — nobody owns this. Deliberately loud; this is how gaps in a process surface.
  • Amber dashed connector labelled ⇄ Handoff — work crossing departments. Handoffs are where things get dropped, so they're drawn, not implied.

Working on it

To do thisDo that
Move a blockDrag it. Position saves automatically about a second after you let go.
Connect two blocksDrag from one block's handle to another.
Delete a connectorClick it, then press Backspace or Delete.
Auto-arrangeTidy up — lays the graph out left to right.
Edit a blockClick it; the inspector opens on the right.
Focus one personClick an avatar — everything not theirs dims. Click again to clear.
Open sub-stepsDouble-click a block that has them.

An Unsaved badge appears while writes are still in flight. Loops are allowed — a marketing system that cycles back on itself is real, so cycles aren't blocked.

The inspector

Title · Goal / purpose · Department · Responsible · Estimated hours · Materialise as · Incoming · Revision. The hours field is hidden on sub-steps, since they can't carry hours.

The rollup strip

Along the bottom: hours per department, a count of unassigned blocks, and a total. For a service system this should match the allocation on Services → [service].

5. Revisions — changing a system safely

Publishing a system changes what lands in someone's ClickUp task list, so it needs approval.

1
Edit the steps however you like. Draft edits never reach ClickUp.
2
Click Propose changes. A reason for change is required — the dialog won't submit without one.
3
The proposal shows a before / after diff: added, removed, and changed steps, with which of title, hours, department, owner or materialise-as moved.
4
An admin or owner clicks Approve — or Request changes to send it back to draft.
5
On approval the new revision publishes and the previous one is marked superseded, in a single database transaction. A system can never have two live revisions.
Two things to know

Existing projects never change. A revision affects future materialisation only. Work already pushed to ClickUp is a frozen snapshot of the system as it stood.

Staff can't propose yet. The spec says they should, but /systems is admin/owner-only, so in practice proposals are an admin/owner action today.

Don't publish a revision and then edit the service's steps

The service editor replaces steps with fresh ones. A published revision points at the old ones, and the push drops steps it can no longer find — so that service would push zero step tasks. Nothing has been published yet, so this hasn't bitten anyone. Pick one or the other per service until it's fixed.

6. How steps reach ClickUp

This part is live right now, whether or not you merge the screens.

Each step has a Materialise as setting, edited in the canvas inspector:

SettingWhat appears in ClickUp
task (default)A subtask under the project, carrying assignee, time estimate, points and due date. Its sub-steps become that task's checklist.
checklist_itemJust a checklist item on the service × department task. No task of its own.
noneNothing in ClickUp. The step still shows in Conductor's workflow timeline with zero actual hours.

Sub-steps never get their own task. If their parent isn't a task, they roll up as checklist items on the service × department task rather than disappearing.

Live issue: ClickUp's parent rollup now double-counts

Step tasks previously carried no time estimate. They do now — and they sit under the same ClickUp parent as the service × department task, whose estimate comes from the same hours. So the parent's rolled-up estimate is roughly double.

Conductor's own numbers are unaffected — actuals are tracked per step instance, and nothing in Conductor reads ClickUp's estimate. It's the ClickUp project view that reads high.

The fix is a judgement call per service: decide whether the detail belongs as step tasks or as the department task, and set the other side to checklist_item or none. Because task is the default, every existing step currently counts twice.

Internal systems create nothing

A kind='internal' system writes nothing to ClickUp, ever. Time is already collected by the perpetual [Internal] {name} — {category} tasks. The system detail page shows an Overhead consumed panel — actual hours from those tasks against the sum of the system's step estimates. That's how you find out the sales system is budgeted at 14h and consuming 30.

7. Known gaps

Honest list. None of these are mysteries — they're all understood and written up.

GapConsequence
ClickUp rollup double-countsLive. Needs a per-service Materialise as decision. See section 6.
Never tested against real ClickUpRequest payloads are unit-tested; no push has been made to a live workspace. The first real quote push is the test.
Staff can't propose revisions/systems is admin/owner-only. Contradicts the spec; needs a product decision.
Published revision + service editWould push zero step tasks for that service. See section 5.
Checklist absorption unexercisedNo service had checklist items when the migration ran, so that path has never seen real data.

A sensible first session

  1. Merge the branch and npm install.
  2. Open Systems, filter to Unmapped / no goal, and write real goals.
  3. Pick one service. Decide its Materialise as split, so its ClickUp estimate stops doubling.
  4. Push one quote for that service and check the ClickUp shape by eye — subtasks, checklist, assignees, estimates.
  5. Only then create an internal system for sales or marketing and map out its steps.
