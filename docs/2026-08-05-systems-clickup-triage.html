Triage: three findings that change the shape

Read these before deciding anything — one of them reverses the request.

ALREADY BUILT Service → process steps → ClickUp already runs on every project push
push-to-clickup/index.ts:570-640 already reads process_steps for every service on the quote, flattens them into one global ordinal sequence, writes process_step_instances, and creates one ClickUp subtask per step named [Step N] {title} parented to the project task. Then sync-clickup-actuals:230-289 pulls status and time_spent back onto each instance. The loop you're describing is closed already — the linkage isn't missing, it's just invisible in the UI and anaemic in what it sends.
THE ACTUAL BUG Conductor has two unrelated concepts both called "the list of things to do"
services.checklist_items text[] (a newline textarea in ServiceDetail.tsx:106) produces a real ClickUp checklist via addClickupChecklist — but it's stamped on the service × department task, and has zero connection to process_steps. So the same service has a documented process and a separate hand-typed checklist, maintained independently, that can silently disagree. That's the thing to fix, and your request is the opportunity to fix it.
DON'T DO THIS Turning steps into ClickUp checklist items would break the actuals loop
ClickUp checklist items cannot hold time. They have no time_spent, no start_date, no date_closed, and status collapses from your five states to a boolean. sync-clickup-actuals joins via GET /api/v2/task/{id}, which doesn't resolve checklist-item ids at all — so actual_hours would be permanently 0, process_step_handoffs would compute nothing, and the est-vs-actual reality check dies. Steps must stay tasks. But there's a better place for checklists — see below.

This also sharpens your "clickable steps" idea. Rather than a click that toggles ClickUp on or off, make it set a mode per step — materialise_as: 'task' | 'checklist_item' | 'none'. Your "two types" is really four destinations

The binary hides the fact that Conductor already has three separate provisioning mechanisms, and the sales system you want to map already has a ClickUp home you may have forgotten about.

Service process
kind: service
Attached to a service. Materialises when a quote is pushed — one subtask per step under the project parent, checklist items inside each. Pipeline exists in push-to-clickup; it just needs assignee, estimate and due date added, and the sub-block checklist wired in.
Exists — enrich it
Recurring / retainer process
kind: recurring
Attached to retainer_recurring_services. Materialises per period via provision-retainer-period — dated tasks or one perpetual [Live] task depending on the member's tracking_mode. Already calls addClickupChecklist at line 488, so the sub-block wiring lands here almost free.
Exists — enrich it
Internal system
kind: internal
Sales, marketing, hiring, admin. These already have a ClickUp home — the perpetual [Internal] {name} — Sales & BD tasks that provision-ongoing-tasks creates against time_categories, which Rize already feeds. The process defines the shape of the work; the ongoing task collects the time. Map the process to a time_category and you get overhead attribution for free, with no new tasks.
Exists — needs a link
Reference only
kind: reference
"How we handle a client complaint." "What happens when someone resigns." Triggered by events, not scheduled — there is genuinely nothing to provision. This is your real "can't be actioned" type, and it's the only one of the four that needs new behaviour: a skip flag. Today push-to-clickup has no per-service or per-step skip condition at all — everything gets pushed.
Genuinely new

Recommended sequence

Ordered so each step is independently useful and nothing is thrown away. The first two are cleanup you'd want regardless of the canvas.

1
Fix the anaemic step tasks
Make push-to-clickup send assignee, time_estimate and points on step subtasks. buildBriefTaskBody in _shared/clickup.ts:141 already does exactly this for the other pipeline — reuse it rather than writing a second version. You're currently computing estimated_hours and department_id per step and then throwing them away at the API boundary. Pure win, no schema change, no canvas required.
~2 days
2
Absorb checklist_items into the process
Add parent_id to process steps so a step can have sub-steps, then generate the ClickUp checklist from those instead of the free-text array. Migrate existing services.checklist_items rows into sub-steps and deprecate the column. Kills the duplicate concept before the canvas can make it worse.
~3 days
3
Add kind and materialise_as
One enum on the process (service | recurring | internal | reference), one on the step (task | checklist_item | none). Add the skip condition to push-to-clickup that doesn't exist yet. This is the whole of your "two types" ask, done as data rather than as two separate code paths.
~3 days
4
Untether process from service
Make process_steps.service_id nullable, add process_definitions with a mandatory goal. Now you can document the sales system — and point it at the sales-bd time_category so its hours land in the overhead view you already have.
~1 week
5
Then build the canvas
Lane-free React Flow board on top of a data model that already knows how to reach ClickUp. Clicking a block to set its materialise mode is now a one-line mutation, because the plumbing was fixed in steps 1–3. Building the canvas first would mean building it against three inconsistent pipelines.
4–6 weeks
Worth naming: when we scoped this you said blueprint-only, no execution link — and that decision was doing real work, because it's what kept the build small. Linking steps to ClickUp turns the canvas from documentation into infrastructure: a change to a process map now changes what appears in someone's task list, which means revisions need approval before they can publish, and a bad edit has operational consequences rather than just documentary ones. That's a good trade, but it makes the Ledger layer (Concept 5) load-bearing rather than optional. Worth choosing deliberately rather than drifting into.
